# 2026-07-20 修改紀錄

## 排查 run_17 評估結果為 0 的原因

- `checkpoints/Mistral-7B-v0.1/run_17/checkpoint-10250/trainer_state.json` 顯示訓練在 step ~3420 附近開始發散（eval_loss 從最低點 ~1.66 瞬間跳到 step 3520 的 28.27），之後直到 step 10250 訓練結束都卡在 eval_loss 3.1~3.9，從未恢復
- `lora_final` 是最後一步（checkpoint-10250）的複製，也就是已發散、劣化的版本；`util/train.py` 先前沒有 `load_best_model_at_end`，Trainer 只會保留最後一個 checkpoint 當作最終產出
- 對應 `gen/eval_results_id5_run_17_Mistral7B_id5_COMB.jsonl`：5000 筆全數 `min_cracked_guess_number=0`（0% crack rate），其中 3227 筆連候選都生不出來，其餘候選內容也明顯偏離正確密碼規律
- 懷疑主因是 `learning_rate=5e-4` 對此 LoRA 設定偏高（run_15 用同樣數值時已觀察到 eval_loss 上升的跡象）

## util/train.py

- `build_training_args()` 的 `TrainingArguments` 新增 `load_best_model_at_end=True`、`metric_for_best_model="eval_loss"`、`greater_is_better=False`
- 效果：即使訓練中途發散或被中斷，HF Trainer 的 checkpoint 輪替邏輯（`_rotate_checkpoints`）會持續保護 `state.best_model_checkpoint`（每次存檔時比較、每次輪替時排除），不受 `save_total_limit=5` 影響而被刪除；訓練正常跑完時也會自動把最佳權重載回並存成 `lora_final`

## train_h200.sh

- 移除失效的 `--resume checkpoints/Mistral-7B-v0.1/run_17/checkpoint-4260`（該 checkpoint 已被輪替刪除、路徑不存在），改回 `python run_train.py` 全新啟動一輪訓練

## 清理 run_17 舊資料

- 刪除整個 `checkpoints/Mistral-7B-v0.1/run_17/`（2.8G，訓練中途發散、最終權重已劣化，使用者確認不需保留）
- 現存最大 run 目錄為 `run_16`，下次 `python run_train.py` 會依 `_next_run_dir` 自動遞增邏輯重新建立 `run_17`
- `learning_rate` 維持 `5e-4` 不變（使用者決定沿用，靠新增的 `load_best_model_at_end` 保底，即使中途再次發散也不會弄丟最佳 checkpoint）
