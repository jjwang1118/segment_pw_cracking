## 2026-06-03 效能修正紀錄

### 問題背景

訓練與預處理執行越來越慢，主因有四：
1. `dataset.map(batched=False)` 逐筆處理，Arrow cache 寫入次數過多
2. `prompt_template` 在每筆樣本中重複 tokenize（固定字串卻每次重算）
3. 模型以 fp32 載入，VRAM 佔用量是 bfloat16 的兩倍，記憶體壓力隨訓練增大
4. `dataloader_num_workers` 未設定，資料載入阻塞訓練主進程

---

### 修改內容

#### 1. `util/pw_tokenize.py`

**位置：** `process_train_targeted` 函數（原第 33 行起）

| 項目 | 修改前 | 修改後 |
|---|---|---|
| 函數簽名 | `(example, tokenizer, prompt_template, vocab, max_length=512)` | `(batch, prompt_ids, vocab, tokenizer, max_length=512)` |
| 處理模式 | 單筆（`batched=False`） | 批次（`batched=True`），輸入輸出皆為 dict of lists |
| prompt tokenize | 函數內部每筆都呼叫 `tokenizer(prompt_template, ...)` | 移除，改由外部傳入已計算好的 `prompt_ids` |

**重點變更說明：**
- `batch` 取代 `example`，接收 HuggingFace datasets `batched=True` 的 dict of lists
- `prompt_ids` 直接傳入（`list[int]`），不再在函數內重複 tokenize
- 內部改為 `for` 迴圈逐筆處理後，回傳三個 list 組成的 dict

### VRAM OOM 風險修正 — 2026-06-03（第二批）

#### 背景

訓練啟動後發現 RTX 5070（12 GB）剩餘 VRAM 僅 171 MiB，觸發 evaluation 或 checkpoint 儲存時有 OOM 風險。

#### 修改內容

##### 1. `config/train_config.yaml`

| 參數 | 修改前 | 修改後 | 原因 |
|---|---|---|---|
| `per_device_eval_batch_size` | `16` | `4` | Eval batch 為訓練的 4×，activation 暴增，171 MiB 不足以承受峰值 |
| `logging_steps` | `1` | `10` | 每步寫 TensorBoard log 產生不必要的 I/O 與記憶體 overhead |

##### 2. `util/train.py` — `build_training_args` 函數

新增參數：
```python
gradient_checkpointing=True,
```
以重新計算換空間：前向傳播不保留全部 activation，反向傳播時重算。預估可釋放 2–4 GB VRAM，使訓練更穩定。

#### 預期效果

| 修改項目 | 預期效果 |
|---|---|
| `per_device_eval_batch_size: 4` | Eval 峰值 VRAM 降至與訓練相當，消除 OOM 風險 |
| `logging_steps: 10` | 減少無謂的磁碟寫入與記憶體壓力 |
| `gradient_checkpointing=True` | 釋放約 2–4 GB VRAM，提供足夠安全邊際 |

### 二、修正 KV Cache 與新版 transformers 的相容性問題

#### 問題背景

transformers >= 4.38 起，`model.forward()` 回傳的 `past_key_values` 為 `DynamicCache` 物件（繼承自 `Cache`），而非舊式 `tuple[tuple[Tensor]]`。  
`util/search.py` 的 cache 操作函數（`_reorder_cache` 等）均以 legacy tuple 為前提撰寫，導致兩個錯誤：

**錯誤一（transformers >= 4.38）**

```
AttributeError: 'NoneType' object has no attribute 'index_select'
```

`DynamicCache` 迭代時部分 layer 的 `past_state` 為 `None`，直接呼叫 `.index_select()` 失敗。

**錯誤二（transformers >= 4.43）**

```
AttributeError: 'tuple' object has no attribute 'get_seq_length'
```

`LlamaModel.forward` 第 401 行：
```python
past_seen_tokens = past_key_values.get_seq_length() if past_key_values is not None else 0
```
此版本移除了自動將 legacy tuple 轉換為 `DynamicCache` 的邏輯，直接對 tuple 呼叫 `.get_seq_length()` 而失敗。

#### 修改內容

##### 1. 新增 `_to_legacy_cache`（`util/search.py`）

```python
def _to_legacy_cache(past_key_values):
    try:
        from transformers.cache_utils import Cache
        if isinstance(past_key_values, Cache):
            return past_key_values.to_legacy_cache()
    except (ImportError, AttributeError):
        pass
    return past_key_values
```

供內部 cache 操作使用，將 `DynamicCache` 轉為 `tuple[tuple[Tensor]]`。

##### 2. 新增 `_from_legacy_cache`（`util/search.py`）

```python
def _from_legacy_cache(past_key_values):
    if not past_key_values:
        return past_key_values
    try:
        from transformers.cache_utils import DynamicCache, Cache
        if not isinstance(past_key_values, Cache):
            return DynamicCache.from_legacy_cache(past_key_values)
    except (ImportError, AttributeError):
        pass
    return past_key_values
```

在傳入 `model.forward()` 前將 legacy tuple 還原為 `DynamicCache`，滿足新版 transformers 的要求。

##### 3. 修正四個 cache 操作函數（None 安全處理）

| 函數 | 修改內容 |
|---|---|
| `_reorder_cache` | `past_state.index_select(...)` 改為 `... if past_state is not None else None` |
| `_merge_cache` | `torch.cat([s1, s2], dim=0)` 改為有 None 保護的條件式 |
| `_cache_slice` | `past_state[:, :, prompt, :]` 改為有 None 保護的條件式 |
| `_cache_concat` | `torch.cat([s1, s2], dim=2)` 改為有 None 保護的條件式 |

##### 4. 套用轉換的位置（`contrastive_search` 函數）

| 位置 | 修改 |
|---|---|
| 初始 forward 後 | `info_cache = _to_legacy_cache(outputs.past_key_values)` |
| 迴圈 forward 輸入 | `past_key_values=_from_legacy_cache(cache)` |
| 迴圈 forward 輸出 | `_cache_slice(_to_legacy_cache(outputs.past_key_values), ...)` |

#### 完整 cache 資料流

```
model.forward() → DynamicCache
                      ↓ _to_legacy_cache()
                  legacy tuple  ← reorder / merge / slice / concat 在此格式下操作
                      ↓ _from_legacy_cache()
                  DynamicCache  → model.forward()（滿足 transformers >= 4.43）
```

### 四、`util/search.py` — `min_len` 在 beam search 內強制執行

#### 背景

`min_len` 只在存檔時過濾治標不治本：EOS 在前幾層就觸發，佔用 `eos_list` 名額，最終有效密碼不足。

#### 修改內容

`contrastive_search` 新增 `min_len: int = 0` 參數，在 EOS 判斷前加層數檢查：

```python
batch_eos_over_threshold_index = (
    torch.where(batch_word_probs[:, -1] >= eos_threshold)[0]
    if l >= min_len - 1
    else torch.empty(0, dtype=torch.long, device=device)
)
```

效果：密碼長度 < `min_len` 時 EOS 完全被忽略，beam 繼續延伸。

### 3. `run_search.py` — 兩個 runner 補齊 id=4 支援

**問題**：`run_contrastive_search` 與 `run_dynamic_beam_search` 均使用 `get_alpa()`（不含 `\n`），且未計算 `newline_id`、未傳 `seg_separator_id`，導致 template id=4 時：
1. `\n` 不在合法 vocab 內，模型無法輸出 segment 分隔符
2. 即使能輸出，結果序列也不會被剝離

**修改**（兩個 runner 均套用相同邏輯）：
- import `get_alpa_with_newline`
- `template_id` 從 cfg 讀取後，依其值選擇 vocab 函數與計算 `newline_id`：

```python
template_id = cfg.get("prompt_template_id", 0)
vocab_dict = get_alpa_with_newline(tokenizer) if template_id == 4 else get_alpa(tokenizer)
newline_id = tokenizer('\n', add_special_tokens=False)['input_ids'][-1] if template_id == 4 else None
# vocab_list 構建時，id=4 將 newline_id 插入 char_ids 與 eos_id 之間
vocab_list = char_ids + ([newline_id] if newline_id is not None else []) + [eos_id]
```

- search 呼叫補上 `seg_separator_id=newline_id`
- `_get_indice(template_id)` 改用已讀取的變數（避免重複呼叫 cfg.get）

## 2026-06-25

### 背景：模型不遵守 Prompt 長度約束

Prompt id=3 透過自然語言描述告知每個 segment 的字元類別與長度（如 `"A sequence of exactly 6 digit characters (0-9)."`），但實際推理時模型可能提早發出 EOS，導致 `number6` 只生成 1 個數字。

**根本原因**：LLM 的 prompt 描述是 soft guidance，不是 hard constraint。beam search 本身對長度和字元類別沒有任何強制機制。

**解決方案**：在 beam search 每個 step 動態限制可選 token，把 soft guidance 升級為 hard enforcement — Constrained Decoding。

### 一、調查 — Prompt id=3 / id=4 是否真的傳達長度

對 `src/prompt_template.py` 進行完整追蹤：

| Tag 類型 | id=3 (`get_explanation`) | id=4 (`expand_tag_description`) | 有長度？ |
|---|---|---|---|
| `number6` | `"A sequence of exactly 6 digit characters (0-9)."` | `"number6 — 6-digit number"` | ✅ |
| `char5` | `"A sequence of exactly 5 pure alphabetic characters."` | `"char5 — 5-character alphabetic string"` | ✅ |
| `special1` | `"Exactly 1 non-alphanumeric special character..."` | `"special1 — 1 special character"` | ✅ |
| `nn` | `"A singular common noun."` | `"nn — singular common noun"` | ❌ |
| `fname` | `"A female given name."` | `"fname — female given name"` | ❌ |

**結論**：backoff tags（`numberN` / `charN` / `specialN` / `mixedN`）兩個 template 都告訴了模型確切長度；pos/semantic tags 因 tag 本身不編碼長度，任何 template 都無法提供。Constrained Decoding 對 backoff tags 效益最大。

### 二、`util/search.py` — 新增 Constrained Decoding

#### `build_step_constraints(tags_str, vocab_dict, eos_id)`

將 Tags 字串展開為 per-step 的允許 token ID 列表：

```python
# "char5|number3|special1" →
step_char_ids = [
    alpha_ids,    # step 0-4 (char5)
    digit_ids,    # step 5-7 (number3)
    special_ids,  # step 8   (special1)
]
total_length = 9
```

含任何 pos/semantic tag → 回傳 `(None, None)`（長度未知，無法展開）。

字元集分類（基於 Python 內建）：

```python
digit_ids   = [tid for c, tid in vocab_dict.items() if c.isdigit()]    # 10 chars
alpha_ids   = [tid for c, tid in vocab_dict.items() if c.isalpha()]    # 52 chars
special_ids = [tid for c, tid in vocab_dict.items() if not c.isalnum()] # 33 chars
any_ids     = list(vocab_dict.values())                                  # 95 chars
```

#### `dynamic_beam_search_Constrained_Decoding(...)`

在 `dynamic_beam_search` 基礎上的三個核心修改：

**1. Per-step Vocab Tensor 替換**

每個 step 前更新 `beam.vocab_tensor`，使 `update_by_prob` 內的索引解碼正確對應當前字元集：

```python
beam.vocab_tensor = step_vocab_tensors[l]   # [cur_char_ids..., eos_id]
beam.update_by_prob(bw, reserve_width, word_probs, pw_past_key_values)
```

**2. Word Probs 跨 Step 銜接**

Step `l` 的 forward pass 產生的 `word_probs` 用於 step `l+1`，因此 remap 必須用 **next step 的 vocab**：

```python
# step l 的 forward pass 內（非最後 step）
logits = remap_logits(next_vtensor, outputs.logits)[:, -1, :]
word_probs = cat([word_probs, log_softmax(logits)[:, :-1]])  # 排除 EOS 欄
```

**3. EOS 處理**

- 非最後 step：完全不收集 EOS（beam 不允許提前結束）
- 最後一個 step：強制對所有存活 beam 收集 EOS，使用 full-vocab `log_softmax` 保證機率正規化

```python
if is_last_step:
    eos_log_probs = log_softmax(outputs.logits[:, -1, :], dim=-1)[:, eos_id]
    batch_eos_probs = beam.search_prob[start:end, 0] + eos_log_probs
    eos_list.extend(zip(eos_seqs, batch_eos_probs))
```

**Beam Width 上界**：每 step 受字元集大小限制（`digit` → 最多 10 分支）：

```python
step_bws[0] = min(beam_width, len(step_char_ids[0]))
step_bws[l] = min(beam_width, step_bws[l-1] * len(step_char_ids[l]))
```

### 七、`util/search.py` — 效能修正

#### 問題一：`output_hidden_states=True` 用在全部 beams

`contrastive_search` 的所有 forward pass 都設 `output_hidden_states=True`（line 551 舊版），導致：

1. Qwen3-4B 36 層的所有中間 hidden states 每次都被 materialize 並回傳
2. **search-extension beams**（`i >= beam_forward_num`）的 hidden states 根本用不到——penalty 對這些 beam 直接設為 `torch.zeros()`——但仍消耗傳輸頻寬與記憶體

**修法**：引入 `need_hidden` flag：

```python
need_hidden = use_contrastive and i < beam_forward_num
outputs = model.forward(..., output_hidden_states=need_hidden)

if need_hidden:
    current_hidden = outputs.hidden_states[-1][:, -1, :]
    penalty = beam.compute_contrastive_penalty(current_hidden, ...)
    hidden_states_batch.append(current_hidden)
else:
    penalty = torch.zeros(end - start, device=device)
```

#### 問題二：Prompt KV Cache 每次 forward 實體複製 `batch_size` 份

三個搜尋函式（`dynamic_beam_search`、`contrastive_search`、`dynamic_beam_search_Constrained_Decoding`）都使用：

```python
_reorder_cache(beam.info_cache, reorder_info_cache_index[:end - start])
```

`reorder_info_cache_index` 永遠是全零，`index_select` 會製造 `batch_size` 份 prompt KV cache 的實體複製。Qwen3-4B 36 層、prompt 約 300 token 時，一次 forward 就多分配數百 MB，在 12GB 顯卡上造成明顯 memory pressure。

**修法**：新增 `_expand_cache()` helper，用 `expand`（zero-copy view）取代 `index_select`：

```python
def _expand_cache(cache: DynamicCache, batch_size: int) -> DynamicCache:
    new = DynamicCache()
    for i, layer in enumerate(cache.layers):
        k = layer.keys.expand(batch_size, -1, -1, -1)
        v = layer.values.expand(batch_size, -1, -1, -1)
        new.update(k, v, layer_idx=i)
    return new
```

三個函式的 `_reorder_cache(beam.info_cache, ...)` 全換為 `_expand_cache(beam.info_cache, end - start)`。

### 八、`util/search.py` — 新增 `contrastive_search_Constrained_Decoding`

結合 `dynamic_beam_search_Constrained_Decoding` 的 hard constraint 與 `contrastive_search` 的多樣性懲罰。

#### 核心設計

| 特性 | 來源 |
|---|---|
| Per-step vocab 限制（char/digit/special/any） | `dynamic_beam_search_Constrained_Decoding` |

| Per-beam 餘弦相似度懲罰 | `contrastive_search` |
| `output_hidden_states` 只用在 beam-width beams（非 search extension、非最後 step） | 本次新增 |

#### `use_contrastive=False` 的處理

當 `use_contrastive=False` 時直接 delegate 到 `dynamic_beam_search_Constrained_Decoding`，不重複邏輯：

```python
if not use_contrastive:
    return dynamic_beam_search_Constrained_Decoding(...)
```

#### EOS 懲罰分離

最後 step 強制收集 EOS 時，`need_hidden` 設為 `False`（所有 batch 都是），節省最後一輪的 hidden state 傳輸：

```python
need_hidden = (i < beam_forward_num) and (not is_last_step)
```

### 修正 SentencePiece tokenizer 的 token ID 錯位問題

#### 問題根因
`get_alpa()` 對 SentencePiece tokenizer（Mistral/LLaMA）存在兩個 bug，導致 Mistral-7B 評估破解率為 0：

1. **`▁X` space-prefix 問題**：`tokenizer(w)["input_ids"][-1]` 取到的是帶 space-prefix 的 `▁d` token。
   組合 decode 時，第 2 個以後的每個 token 都會前置空白：
   `decode([▁d, ▁r, ▁a]) → "d r a"` ≠ `"dra"`，密碼永遠比對不上。

2. **推論 decode 直接與 `real_pw` 比對**（`run_eval.py:309`），而非做任何後處理，
   因此上述空白導致 1000 個候選全部 miss。

#### 修改內容

##### `util/pw_tokenize.py` — `get_alpa()`
- 加入 SentencePiece 偵測：對 `"d"` 和 `"r"` 組合 decode，若結果 ≠ `"dr"` 即為 SPM。
- SPM 路徑：優先查 byte-level token `<0xHH>`（如 `<0x64>` for `d`），組合 decode 不帶空白。
  fallback 順序：`<0xHH>` → `convert_tokens_to_ids(w)` → pipeline。
- tiktoken（Qwen）路徑：原邏輯不動。

##### `run_eval.py` — `run_eval()`
- 在 vocab 初始化後加入 `_needs_space_strip` flag，用 `vocab_dict['d']` 做 probe（而非重新 tokenize），
  確保 `get_alpa()` 修正後此 flag 自動關閉。
- decode 候選時若 flag 為 True，呼叫 `.replace(" ", "")` 去除殘留空白。

#### 驗證
| Tokenizer | 修前 `encode→decode("dragon99!")` | 修後 |
|---|---|---|
| Mistral-7B SentencePiece | `"d r a g o n99 !"` ✗ | `"dragon99!"` ✓ |
| Qwen3-4B tiktoken | `"dragon99!"` ✓ | `"dragon99!"` ✓（不受影響）|

#### 後續行動
- 使用修正後的 `get_alpa()` 重新訓練 Mistral-7B（run_3/template_5 需要 retrain）。
- 重訓完成後，`_needs_space_strip` 對 Mistral 也會自動為 False（byte token 個別 decode 正確）。

## 2026-06-29

### fix: revert get_alpa() SPM strategy + fix _needs_space_strip probe

#### 問題背景

`8a8420d` 嘗試用 byte-level token `<0xHH>` 解決 SentencePiece 組合 decode 帶空格的問題，
但引入了新 bug：model 訓練時的輸出 token 是 `▁X`（encode_limit 使用 get_alpa() 建立
訓練 label），byte token 是 model 從未生成過的 OOD token，constrained beam search 在
byte token 空間搜尋時 model 機率近乎 0，beam 崩潰 → 所有 candidate 退化成固定前綴
（如 `70000000a`, `aaaaaa00`）。

此外，原 `_needs_space_strip` 探針用單字元 decode([▁d]) == "d" 判斷，
但 SPM 單 token decode 不帶空格（多 token 組合才帶），探針給 false negative，
導致空格無法被剝除。

#### 修改內容

**`util/pw_tokenize.py` — `get_alpa()`**

- 移除 byte-level token fallback（`<0xHH>` 方案）
- 恢復 SPM branch 使用 `▁X` tokens：`tokenizer(w, add_special_tokens=False)['input_ids'][-1]`
  - 這與 `encode_limit()` 建立訓練 label 時使用的 token 一致
  - model 在 constrained search 時的機率分佈有意義
  - combined decode 帶空格，由 caller 處理（`_needs_space_strip`）
- 新增 model-aware 分流說明（tiktoken vs SentencePiece），兩種策略明確分開記錄
- 保留 SPM 偵測邏輯（`_is_spm` flag），作為文件與未來擴充點

**`run_eval.py` — `_needs_space_strip` 探針**

- 改為雙字元組合 decode 探針：
  `tokenizer.decode([vocab['d'], vocab['r']]) != "dr"`
- 單字元 probe 對 SPM 無效（單 token decode 不帶空格）
- 雙字元 probe 正確區分 SPM（"d r"）與 tiktoken（"dr"）

#### 預期效果

- SPM (Mistral) constrained search：搜尋正確的 `▁X` token 空間 → model 機率有意義
- decoded candidate 帶空格（`"7 0 0 0 0 0 0 0 a"`）→ `_needs_space_strip=True` → strip → `"70000000a"`
- tiktoken (Qwen)：不受影響，行為不變

#### 注意

此修復只解決 token mapping / decode 問題。Mistral run_3 LoRA 的
per-position 機率分佈退化（始終輸出 `70000000a`、`aaaaaa00`）是獨立的
訓練品質問題，需要另行分析（id=5 template 對 Mistral SPM 訓練的適配性）。
