# 修改紀錄 — 2026-06-25

---

## 背景：模型不遵守 Prompt 長度約束

Prompt id=3 透過自然語言描述告知每個 segment 的字元類別與長度（如 `"A sequence of exactly 6 digit characters (0-9)."`），但實際推理時模型可能提早發出 EOS，導致 `number6` 只生成 1 個數字。

**根本原因**：LLM 的 prompt 描述是 soft guidance，不是 hard constraint。beam search 本身對長度和字元類別沒有任何強制機制。

**解決方案**：在 beam search 每個 step 動態限制可選 token，把 soft guidance 升級為 hard enforcement — Constrained Decoding。

---

## 一、調查 — Prompt id=3 / id=4 是否真的傳達長度

對 `src/prompt_template.py` 進行完整追蹤：

| Tag 類型 | id=3 (`get_explanation`) | id=4 (`expand_tag_description`) | 有長度？ |
|---|---|---|---|
| `number6` | `"A sequence of exactly 6 digit characters (0-9)."` | `"number6 — 6-digit number"` | ✅ |
| `char5` | `"A sequence of exactly 5 pure alphabetic characters."` | `"char5 — 5-character alphabetic string"` | ✅ |
| `special1` | `"Exactly 1 non-alphanumeric special character..."` | `"special1 — 1 special character"` | ✅ |
| `nn` | `"A singular common noun."` | `"nn — singular common noun"` | ❌ |
| `fname` | `"A female given name."` | `"fname — female given name"` | ❌ |

**結論**：backoff tags（`numberN` / `charN` / `specialN` / `mixedN`）兩個 template 都告訴了模型確切長度；pos/semantic tags 因 tag 本身不編碼長度，任何 template 都無法提供。Constrained Decoding 對 backoff tags 效益最大。

## 二、`util/search.py` — 新增 Constrained Decoding

### `build_step_constraints(tags_str, vocab_dict, eos_id)`

將 Tags 字串展開為 per-step 的允許 token ID 列表：

```python
# "char5|number3|special1" →
step_char_ids = [
    alpha_ids,    # step 0-4 (char5)
    digit_ids,    # step 5-7 (number3)
    special_ids,  # step 8   (special1)
]
total_length = 9
```

含任何 pos/semantic tag → 回傳 `(None, None)`（長度未知，無法展開）。

字元集分類（基於 Python 內建）：

```python
digit_ids   = [tid for c, tid in vocab_dict.items() if c.isdigit()]    # 10 chars
alpha_ids   = [tid for c, tid in vocab_dict.items() if c.isalpha()]    # 52 chars
special_ids = [tid for c, tid in vocab_dict.items() if not c.isalnum()] # 33 chars
any_ids     = list(vocab_dict.values())                                  # 95 chars
```

### `dynamic_beam_search_Constrained_Decoding(...)`

在 `dynamic_beam_search` 基礎上的三個核心修改：

**1. Per-step Vocab Tensor 替換**

每個 step 前更新 `beam.vocab_tensor`，使 `update_by_prob` 內的索引解碼正確對應當前字元集：

```python
beam.vocab_tensor = step_vocab_tensors[l]   # [cur_char_ids..., eos_id]
beam.update_by_prob(bw, reserve_width, word_probs, pw_past_key_values)
```

**2. Word Probs 跨 Step 銜接**

Step `l` 的 forward pass 產生的 `word_probs` 用於 step `l+1`，因此 remap 必須用 **next step 的 vocab**：

```python
# step l 的 forward pass 內（非最後 step）
logits = remap_logits(next_vtensor, outputs.logits)[:, -1, :]
word_probs = cat([word_probs, log_softmax(logits)[:, :-1]])  # 排除 EOS 欄
```

**3. EOS 處理**

- 非最後 step：完全不收集 EOS（beam 不允許提前結束）
- 最後一個 step：強制對所有存活 beam 收集 EOS，使用 full-vocab `log_softmax` 保證機率正規化

```python
if is_last_step:
    eos_log_probs = log_softmax(outputs.logits[:, -1, :], dim=-1)[:, eos_id]
    batch_eos_probs = beam.search_prob[start:end, 0] + eos_log_probs
    eos_list.extend(zip(eos_seqs, batch_eos_probs))
```

**Beam Width 上界**：每 step 受字元集大小限制（`digit` → 最多 10 分支）：

```python
step_bws[0] = min(beam_width, len(step_char_ids[0]))
step_bws[l] = min(beam_width, step_bws[l-1] * len(step_char_ids[l]))
```

## 五、`run_eval.py` — 新增 constrained_beam_search dispatch 分支

**新增 `constrained_vocab_dict`**：與 `vocab_list` 採用相同排除集合（`<`, `|`, `>`, `\t`），避免 `<|...|>` token 污染，但以 dict 形式保留（constrained search 需要 char → id 對應）：

```python
_EXCLUDE = {tokenizer.eos_token, "\t", "<", "|", ">"}
constrained_vocab_dict = {c: tid for c, tid in vocab_dict.items() if c not in _EXCLUDE}
```

**Per-entry dispatch 邏輯**：

```python
if search_type == "constrained_beam_search":
    step_ids, _ = build_step_constraints(tags_str, constrained_vocab_dict, eos_id)
    if step_ids is not None:
        # 全 backoff → constrained decoding
        raw_results = dynamic_beam_search_Constrained_Decoding(...)
    elif c_fallback:
        # 含 pos/semantic → fallback 到 dynamic_beam_search
        raw_results = dynamic_beam_search(...)
    else:
        raw_results = []
```

**`_CANONICAL` 新增**：

```python
"constrained_beam_search": "constrained_beam_search",
```

**`beam_width` 變數重新命名**：原 `beam_width`（list）改為 `beam_width_list`，避免與 constrained search 的單一 int `c_beam_width` 衝突。

## 七、`util/search.py` — 效能修正

### 問題一：`output_hidden_states=True` 用在全部 beams

`contrastive_search` 的所有 forward pass 都設 `output_hidden_states=True`（line 551 舊版），導致：

1. Qwen3-4B 36 層的所有中間 hidden states 每次都被 materialize 並回傳
2. **search-extension beams**（`i >= beam_forward_num`）的 hidden states 根本用不到——penalty 對這些 beam 直接設為 `torch.zeros()`——但仍消耗傳輸頻寬與記憶體

**修法**：引入 `need_hidden` flag：

```python
need_hidden = use_contrastive and i < beam_forward_num
outputs = model.forward(..., output_hidden_states=need_hidden)

if need_hidden:
    current_hidden = outputs.hidden_states[-1][:, -1, :]
    penalty = beam.compute_contrastive_penalty(current_hidden, ...)
    hidden_states_batch.append(current_hidden)
else:
    penalty = torch.zeros(end - start, device=device)
```

### 問題二：Prompt KV Cache 每次 forward 實體複製 `batch_size` 份

三個搜尋函式（`dynamic_beam_search`、`contrastive_search`、`dynamic_beam_search_Constrained_Decoding`）都使用：

```python
_reorder_cache(beam.info_cache, reorder_info_cache_index[:end - start])
```

`reorder_info_cache_index` 永遠是全零，`index_select` 會製造 `batch_size` 份 prompt KV cache 的實體複製。Qwen3-4B 36 層、prompt 約 300 token 時，一次 forward 就多分配數百 MB，在 12GB 顯卡上造成明顯 memory pressure。

**修法**：新增 `_expand_cache()` helper，用 `expand`（zero-copy view）取代 `index_select`：

```python
def _expand_cache(cache: DynamicCache, batch_size: int) -> DynamicCache:
    new = DynamicCache()
    for i, layer in enumerate(cache.layers):
        k = layer.keys.expand(batch_size, -1, -1, -1)
        v = layer.values.expand(batch_size, -1, -1, -1)
        new.update(k, v, layer_idx=i)
    return new
```

三個函式的 `_reorder_cache(beam.info_cache, ...)` 全換為 `_expand_cache(beam.info_cache, end - start)`。

## 八、`util/search.py` — 新增 `contrastive_search_Constrained_Decoding`

結合 `dynamic_beam_search_Constrained_Decoding` 的 hard constraint 與 `contrastive_search` 的多樣性懲罰。

### 核心設計

| 特性 | 來源 |
|---|---|
| Per-step vocab 限制（char/digit/special/any） | `dynamic_beam_search_Constrained_Decoding` |
| 中間 step 禁止 EOS；最後 step 強制 EOS | `dynamic_beam_search_Constrained_Decoding` |
| Hidden state 歷史累積 (`acc_hidden_state`) | `contrastive_search` |
| Per-beam 餘弦相似度懲罰 | `contrastive_search` |
| `output_hidden_states` 只用在 beam-width beams（非 search extension、非最後 step） | 本次新增 |

### `use_contrastive=False` 的處理

當 `use_contrastive=False` 時直接 delegate 到 `dynamic_beam_search_Constrained_Decoding`，不重複邏輯：

```python
if not use_contrastive:
    return dynamic_beam_search_Constrained_Decoding(...)
```

### EOS 懲罰分離

最後 step 強制收集 EOS 時，`need_hidden` 設為 `False`（所有 batch 都是），節省最後一輪的 hidden state 傳輸：

```python
need_hidden = (i < beam_forward_num) and (not is_last_step)
```
