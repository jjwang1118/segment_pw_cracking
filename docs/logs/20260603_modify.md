# 效能修正紀錄 — 2026-06-03

## 問題背景

訓練與預處理執行越來越慢，主因有四：
1. `dataset.map(batched=False)` 逐筆處理，Arrow cache 寫入次數過多
2. `prompt_template` 在每筆樣本中重複 tokenize（固定字串卻每次重算）
3. 模型以 fp32 載入，VRAM 佔用量是 bfloat16 的兩倍，記憶體壓力隨訓練增大
4. `dataloader_num_workers` 未設定，資料載入阻塞訓練主進程

---

## 修改內容

### 1. `util/pw_tokenize.py`

**位置：** `process_train_targeted` 函數（原第 33 行起）

| 項目 | 修改前 | 修改後 |
|---|---|---|
| 函數簽名 | `(example, tokenizer, prompt_template, vocab, max_length=512)` | `(batch, prompt_ids, vocab, tokenizer, max_length=512)` |
| 處理模式 | 單筆（`batched=False`） | 批次（`batched=True`），輸入輸出皆為 dict of lists |
| prompt tokenize | 函數內部每筆都呼叫 `tokenizer(prompt_template, ...)` | 移除，改由外部傳入已計算好的 `prompt_ids` |

**重點變更說明：**
- `batch` 取代 `example`，接收 HuggingFace datasets `batched=True` 的 dict of lists
- `prompt_ids` 直接傳入（`list[int]`），不再在函數內重複 tokenize
- 內部改為 `for` 迴圈逐筆處理後，回傳三個 list 組成的 dict

---

### 2. `util/train.py`

#### 2-1. `build_model_and_tokenizer` 函數（約第 38 行）

| 修改前 | 修改後 |
|---|---|
| `AutoModelForCausalLM.from_pretrained(source)` | `AutoModelForCausalLM.from_pretrained(source, torch_dtype=torch_dtype)` |

新增邏輯：
```python
torch_dtype = torch.bfloat16 if torch.cuda.is_available() else torch.float32
```
有 GPU 時以 bfloat16 載入模型，VRAM 用量減半，減少記憶體碎片化造成的漸進式效能下降。

#### 2-2. `build_training_args` 函數（約第 60 行）

新增參數：
```python
dataloader_num_workers=4,
```
資料載入改為 4 個平行 worker，不再阻塞訓練主進程。

同時修正 `learning_rate` 那一行原本異常的空白縮排。

#### 2-3. `train` 函數（約第 95 行）

**prompt_ids 預計算（新增）：**
```python
# Pre-compute prompt_ids once — avoid re-tokenising the same string for every sample
prompt_ids = tokenizer(prompt_template, add_special_tokens=False)["input_ids"]
if tokenizer.bos_token_id is not None:
    prompt_ids = [tokenizer.bos_token_id] + prompt_ids
```

**`partial` 參數更新：**
```python
# 修改前
preprocess_fn = partial(
    process_train_targeted,
    tokenizer=tokenizer,
    prompt_template=prompt_template,
    vocab=vocab,
    max_length=512,
)

# 修改後
preprocess_fn = partial(
    process_train_targeted,
    prompt_ids=prompt_ids,
    vocab=vocab,
    tokenizer=tokenizer,
    max_length=512,
)
```

**`dataset.map` 改為批次處理：**
```python
# 修改前
datasets["train"].map(preprocess_fn, batched=False, ...)

# 修改後
datasets["train"].map(preprocess_fn, batched=True, batch_size=256, ...)
```

## 預期效果

| 修改項目 | 預期效果 |
|---|---|
| `batched=True, batch_size=256` | 預處理速度顯著提升，Arrow cache 寫入次數大幅減少 |
| `prompt_ids` 預計算 | 消除每筆樣本重複 tokenize 固定字串的 CPU 浪費 |
| `torch_dtype=bfloat16` | VRAM 用量減半，緩解訓練後期記憶體碎片化造成的漸進式變慢 |
| `dataloader_num_workers=4` | 資料載入與訓練計算可平行進行 |

## VRAM OOM 風險修正 — 2026-06-03（第二批）

### 背景

訓練啟動後發現 RTX 5070（12 GB）剩餘 VRAM 僅 171 MiB，觸發 evaluation 或 checkpoint 儲存時有 OOM 風險。

### 修改內容

#### 1. `config/train_config.yaml`

| 參數 | 修改前 | 修改後 | 原因 |
|---|---|---|---|
| `per_device_eval_batch_size` | `16` | `4` | Eval batch 為訓練的 4×，activation 暴增，171 MiB 不足以承受峰值 |
| `logging_steps` | `1` | `10` | 每步寫 TensorBoard log 產生不必要的 I/O 與記憶體 overhead |

#### 2. `util/train.py` — `build_training_args` 函數

新增參數：
```python
gradient_checkpointing=True,
```
以重新計算換空間：前向傳播不保留全部 activation，反向傳播時重算。預估可釋放 2–4 GB VRAM，使訓練更穩定。

### 預期效果

| 修改項目 | 預期效果 |
|---|---|
| `per_device_eval_batch_size: 4` | Eval 峰值 VRAM 降至與訓練相當，消除 OOM 風險 |
| `logging_steps: 10` | 減少無謂的磁碟寫入與記憶體壓力 |
| `gradient_checkpointing=True` | 釋放約 2–4 GB VRAM，提供足夠安全邊際 |
